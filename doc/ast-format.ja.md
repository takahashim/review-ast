# AST ダンプ形式の互換性ポリシー(草案)

本書は、シリアライズ済み AST(JSON ダンプ)の互換性に関する運用規則を定める。
対象は、ダンプを生成する側(review-ast)と、ダンプを読む側(外部レンダラ、解析ツール)の両方である。
形式そのものの意味は [ast-semantics.ja.md](ast-semantics.ja.md) が定め、本書は「いつ、何を、どう変えてよいか」だけを定める。

## 1. 用語と現状

- **エンベロープ**:
  `review-ast-dump` が出力する最上位オブジェクト `{ "ast_format": 1, "generator": "review X.Y.Z", "root": <ノード木> }`。
- **`ast_format`**:
  ダンプ形式の版番号。現在は 1。
  読み込みは厳密一致で、異なる版は明示的なエラーで拒否する。
- **`generator`**:
  生成元を示す情報提供の文字列。
  **読み手はこの値で挙動を分岐してはならない**。分岐してよいのは `ast_format` だけである。
- **正準キー**:
  各ノードのシリアライザが書き出すキー名。
  デシリアライザが受理するのもこの名前だけである(2 章)。

## 2. キーは正準名ひとつ

**各フィールドのキーは正準名ひとつだけとする。デシリアライザは別名を受理しない。**

読み込み側に別名を足せば、同じ意味のフィールドが二通りの綴りで存在することになり、
どちらが正なのかが実装に散らばる。
キー名を変えたくなったら、別名で両対応するのではなく版を上げる(3 章)。

## 3. 版更新の判断基準

### 版を上げずにできる変更

- **省略可能なフィールドの追加**。
  読み手は「知らないキーを無視する」ことを要求される(4 章)。
  したがって追加は既存の読み手を壊さない。
- フィールドの省略条件の緩和(これまで省略していた値を常に書く、など。ただし意味は不変であること)。
- `generator` 文字列の形式変更。

### 版を上げなければならない変更

- キーの改名・削除。
- 既存フィールドの意味・型・単位の変更。
- 構造の変更(`children` の形、エンベロープの形、ノード `type` の改名)。
- 省略時の既定値の意味変更。

判断に迷う場合は「ast_format 1 と宣言された既存の正しい読み手が、新しいダンプを誤読しうるか」で決める。
誤読しうるなら版を上げる。

## 4. 読み手への要求(適合条件)

ダンプを読む実装は、次を満たすこと。

1. `ast_format` を検査し、対応しない版は明示的に拒否する(黙って誤読しない)。
2. 知らないキーは無視する(省略可能フィールドの追加を許容するため)。
3. `generator` で挙動を分岐しない。

読み込み側の版サポートは**単一版**とする。
すなわち「版 N の読み手は版 N だけを読む」。
旧版ダンプの移行経路は、旧版の `review-ast-dump2re` による `.re` への逆生成と再コンパイルである。
複数版の読み込み互換層は持たない(持つ場合、旧版の挙動をテストで固定し続ける長期の義務が生じる。この判断は design-improvements 項目 6 の「ゲートには予算を設ける」と同じ論理である)。

## 5. スキーマとの関係

スキーマの実体は `schema/ast-format-1.schema.json` である。
これは手書きではなく、実ダンプ(`samples/syntax-book` と `samples/md-syntax-book` の全章)を
introspect して `tools/generate_ast_schema.rb` が生成する。
シリアライズの形が変われば `test/ast/test_ast_schema.rb` が失敗するので、
スキーマが黙って古くなることはない(直し方は再生成するだけである)。

```bash
ruby tools/generate_ast_schema.rb
```

生成スキーマ(`additionalProperties: false`)は **gem リリースごとに再生成して同梱**する。
省略可能フィールドの追加は版を上げないため、スキーマは同一 `ast_format` の中でもリリースごとに広がりうる。
したがって検証の規則は次になる。

- 検証は「**生成した gem と同じか、それより新しい**リリースのスキーマ」で行う。
- 古いスキーマで新しいダンプが不合格になるのは想定内であり、形式の破壊ではない(スキーマを更新して再検証する)。
- CI では、スキーマを再生成して同梱物と一致することを検査する(`test/ast/test_ast_schema.rb`)。
  スキーマはコーパスから導出されるため「コーパスが妥当か」は構成上自明であり、
  検査すべきは「同梱スキーマがシリアライザに追随しているか」である。
- ノード定義はすべて閉じている(`additionalProperties: false`)。
  未知のキーは、意図しないシリアライズ変更として検出される。
- `ResolvedData` 系(`ImageReference` 等)はノードではないため `$defs/resolved_data` に分けてある。
  ノードが来るべき位置に置けてはならない。

## 6. bare ノード JSON の地位

エンベロープなしのノード単体 JSON(最上位が `{"type": ...}`)は、**内部用**とする(テスト、部分木の受け渡し)。
外部との交換境界(dump ファイル、他ツールへの受け渡し)では常にエンベロープを用いる。
デシリアライザの bare 受理は互換のため残すが、公開契約には含めない。

## 7. 版更新チェックリスト

`ast_format` を上げるときは、次を 1 コミット(または 1 PR)で行う。

- [ ] `AST_FORMAT_VERSION` を更新する。
- [ ] 旧版で予告した削除を実施する。
- [ ] スキーマを再生成する。
- [ ] 本書の変更履歴(下記)に 1 行追加する。
- [ ] 「旧版ダンプが明示的なエラーで拒否される」テストを更新する。
- [ ] round-trip・render-identity の全スイートが緑であることを確認する。
